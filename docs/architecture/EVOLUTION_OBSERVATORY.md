# Mia Evolution Observatory

The observatory is a core project subsystem from the first experiment record. It must answer: **What changed from Day 0 to Day N, why did it change, and did the change measurably improve Mia?**

## Dashboard sections

1. **Experiment overview:** start date, elapsed day, pause/offline days, current status and source baseline.
2. **Growth trends:** benchmark quality, task success, reliability, autonomy and efficiency over time.
3. **Capability ledger:** created, reused, adapted, composed, improved, rejected, retired and rolled-back capabilities.
4. **SPS layer health:** activity and verification results for each of the ten layers.
5. **Code evolution:** version lineage, diffs, tests, activation and rollback history.
6. **Decision trace:** gap evidence, options considered, decision rationale and governance result.
7. **Resource and cost:** CPU/RAM use, model latency, token use, estimated/actual cost and provider quota state.
8. **Daily reports:** automatically generated summaries based only on stored events and benchmark results.

## Required graphs

- Multi-series line chart: benchmark scores by day and benchmark.
- Line chart: task success and reliability.
- Bar/stacked-bar chart: capability lifecycle events per day.
- Heatmap: ten SPS layers against days, showing events and validation outcomes.
- Resource charts: memory, CPU, latency and inference cost.
- Before/after comparison: selected Day A versus Day B with test-level differences.

Metrics with different units must not be plotted on the same unlabelled scale. A score should include its benchmark definition, version, environment and direction (higher/lower is better).

## Metric catalogue

| Metric | Type | Evidence |
|---|---|---|
| task_success_rate | Outcome | Fixed task suite successes / attempts |
| benchmark_score | Quality | Versioned benchmark run |
| regression_rate | Quality | Failed previously passing tests |
| reliability_rate | Operations | Successful completed tasks / eligible attempts |
| autonomy_completion_rate | Autonomy | Eligible tasks completed without user intervention |
| recovery_rate | Resilience | Recoveries completed without data loss |
| capability_reuse_rate | Reuse | Accepted reuse decisions / capability decisions |
| capability_count | Inventory | Active validated capabilities only |
| activation_failure_rate | Safety/quality | Failed activations / activation attempts |
| rollback_rate | Stability | Rollbacks / activated changes |
| p50_latency_ms / p95_latency_ms | Performance | Measured request timings |
| cpu_seconds / peak_ram_mb | Resource | Process/system measurements with source stated |
| estimated_cost_usd / actual_cost_usd | Cost | Provider usage/billing data, or zero for verified local use |

A larger capability count is not evidence of intelligence. A model's self-reported score is not a benchmark.

## Data integrity

- Store raw benchmark results and test outputs, not only aggregates.
- Use UTC timestamps and explicit Day 0-relative day indices.
- Store source commit, configuration hash, model IDs/versions and environment metadata.
- Never overwrite a baseline or a daily snapshot; append corrections as new events.
- Mark missing days as paused, unavailable or not run, not as zero-performance days.
- Export JSON/CSV and a final reproducibility manifest.
- Dashboard empty states must remain empty; never insert invented sample values.


## Day 0 capture and explicit start

The dashboard captures Day 0 on the computer hosting Mia, not on a GitHub
runner. Capture requires a clean Git working tree, records the full source
commit and an allow-listed configuration fingerprint, runs Ruff and the full
pytest suite with common credential environment variables removed, and stores
test counts, exit codes and output hashes. A failed lint/test run creates no
experiment. The baseline is immutable. The separate **Start experiment**
action is required before Day 1; capturing Day 0 does not start autonomous work.


## Daily evidence capture

Daily snapshots are generated by the Mia host, not submitted as arbitrary client
JSON. The capture endpoint calculates the due day from the experiment's actual
UTC start time, reruns the same clean-checkout Ruff/pytest suite, compares the
suite/configuration and OS/Python/machine identity with Day 0, and records live
CPU/RAM values. It never creates zero-valued placeholders. If Mia was offline,
missing day indices are recorded as unavailable and only the current verified
day is stored. The dashboard enables **Capture today's evidence** only when a daily snapshot
is due. It refreshes due state while open and records missed offline days as
unavailable. Manual capture remains available; the optional host scheduler
below can also capture due days when explicitly enabled. If the final day's
capture window expires, the run becomes terminally incomplete rather than
being reported as completed.


## Automatic daily capture scheduler

The runtime default is disabled when the variable is absent. The supplied
`.env.example` opts in with `MIA_EXPERIMENT_AUTO_CAPTURE=true`; copy it to
`.env` to enable automatic capture. Install the optional `monitoring` extra
for CPU/RAM telemetry. After the
owner explicitly starts an experiment, Mia checks every 60 seconds for a due
snapshot. Before the full local verification suite it checks CPU/RAM against
the configured autonomy thresholds; under pressure it defers and retries
after 15 minutes. The scheduler never starts an experiment, never runs when
there is no explicitly running experiment, and never fills missed days with
invented records. The manual dashboard capture remains available.


### Pause, resume and explicit day records (MIA-OBS-03)

`POST /api/experiments/scheduler/pause` and `/resume` (409 unless the scheduler was opted in with
`MIA_EXPERIMENT_AUTO_CAPTURE=true`) let the owner stop and restart automatic capture without
restarting Mia. `GET /api/experiments/scheduler/status` now reports `paused` and `paused_at`. Pause state
is the newest `daily_snapshot_scheduler_paused` / `_resumed` event, so it survives restarts and is its own
audit trail; repeating a pause or resume records nothing. While paused the scheduler does no telemetry or
capture work.

Every day the scheduler does not capture leaves an explicit event:

| Situation | Event (outcome) |
| --- | --- |
| Owner paused | `daily_snapshot_skipped_paused` (skipped), once per experiment-day |
| CPU/RAM over the limit | `daily_snapshot_deferred_resource_pressure` (deferred) |
| CPU/RAM telemetry unavailable | `daily_snapshot_deferred_telemetry_unavailable` (deferred; error type only, never its text) |
| Capture failed | `daily_snapshot_auto_capture_failed` (failed) |
| Mia was not running | `daily_snapshots_unavailable`, written at the next capture |
| Scheduler on, nothing running | `daily_snapshot_scheduler_noop_day` (no_op), once per UTC day, restart-safe |

The final report lists a paused day under `days.unavailable` (explained), not `days.unaccounted`. A paused day
that is captured after resume is simply recorded. Captures are idempotent: repeated or concurrent checks
record each day once and never log a false failure. Network: the capture path itself opens no sockets (a test
blocks them); the injected baseline capture runs local tools only, and this is not a claim about third-party
code. Limits: no scheduled pause windows, no per-experiment pause, and a day lost to a deferral or failure that is
never retried before the window closes is still reported as unaccounted rather than guessed.

## Final experiment report

The read-only report endpoint is GET /api/experiments/{experiment_id}/report.
It verifies the immutable Day 0 manifest and every daily snapshot hash before
building a report from records linked to that experiment ID. It lists recorded,
missing, explicitly unavailable and unaccounted day indices, plus the linked
events and metric samples. A completed conclusion is allowed only when the
planned final-day snapshot exists; an expired run without it is incomplete.
For an incomplete run the report compares only the latest verified snapshot
(if any) and explicitly labels that comparison non-final. Capability versions
are not attributed by timestamp because the registry is not linked to an
experiment ID. A report object is not evidence of a completed experiment; only
real host-captured records can support that conclusion.
