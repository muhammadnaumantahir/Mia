### Queue and milestone handoff rules

- `OPEN` tasks are candidates, not permission to ignore priority.
- Within a milestone, agents select the highest-priority dependency-ready task matching their specialization.
- A later milestone becomes eligible for parallel work only after every implementation task in the immediately preceding milestone is `DONE` or `IN_PROGRESS` under another agent. An agent must not leave its own earlier-milestone task unfinished to start lower-priority work.
- A task with unmet explicit dependencies is not eligible even if its milestone is unlocked.
- `MIA-M1-13` is the final M1 acceptance gate: it is blocked until all M1 implementation tasks are done. M2 work may be prepared/implemented in parallel after the M1 implementation queue is fully accounted for, but M1 cannot be declared complete until the gate passes.
- Apply the same pattern to milestone acceptance: parallel work can begin once prior work is accounted for; milestone completion still requires all exit criteria.
- The task board is advisory, not an atomic lock. Re-fetch it and its SHA immediately before every claim/write; serialize shared-file writes and main commits.
- Re-audit source/tests before claiming any task; existing implementation may satisfy some or all acceptance criteria. Mark existing work done only with source/test/commit evidence.


## Continue and queue rules

- On every owner **Continue**, each available agent resumes its own `IN_PROGRESS` task before taking new work. A status-only response is not sufficient when development is possible.
- Finish the current bounded task, verify and commit it, then claim the next highest-priority eligible task for that specialization. Continue through additional tasks while the turn budget permits.
- If interrupted by a usage/context limit, checkpoint exact progress in `docs/AI_INTEGRATION_LOG.md`; leave the task `IN_PROGRESS`. The next Continue must resume from that checkpoint, not restart.
- When a specialist has no eligible task, inspect the highest-priority incomplete roadmap gate and add a unique, scoped task. Do not go idle while meaningful work remains.
- Apply the milestone handoff rule: a later milestone may start parallel work when every implementation task in the immediately preceding milestone is DONE or IN_PROGRESS under another agent. If any earlier implementation task remains OPEN, claim it first; never abandon your own earlier task. Explicit dependencies remain mandatory, and the milestone cannot be declared complete until its full exit criteria pass.
- Each agent owns at most one active task. The task board is advisory, not an atomic lock; re-fetch the latest board and SHA immediately before every write.
- Never use duplicate task IDs. If a task is already complete, record evidence and select the next eligible task rather than repeating it.
- A task is `DONE` only after its commit is verified on remote `main` and acceptance evidence is recorded.

## Task update format

Append a concise UTC entry to `docs/AI_INTEGRATION_LOG.md` for every claim, checkpoint, handoff, blocker and completion. Include task ID, agent ID, status, changed paths, exact tests and commit SHA when available.

## Adding tasks

Use unique IDs `MIA-[AREA]-NN`. Every task must state priority, dependencies, allowed paths/ownership boundary, acceptance criteria, test expectations and security/privacy constraints. Avoid vague tasks such as “improve AI”.
